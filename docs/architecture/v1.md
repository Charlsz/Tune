**Versión:** 1.1  
**Fecha:** 2026-08-29  
**Basado en:** [Primer Informe](../PrimerInforme.md) — sección 5

## Visión general

Tune implementa un laboratorio MLOps modular para **fine-tuning eficiente**: ejecuta un baseline y una estrategia optimizada sobre el mismo dataset y el mismo modelo preentrenado, registra cada corrida (parámetros, tiempo, memoria, calidad), compara ambas y sirve el modelo seleccionado mediante **API REST** o CLI.

El modelo concreto (incluido un caso geoespacial, si es viable) valida la arquitectura; no es el eje del sistema.

## Flujo de datos

```text
Dataset versionado + modelo preentrenado
   ↓
Configuración (baseline | optimized)
   ↓
Fine-tuning
   ↓
Tracking (parámetros, métricas, tiempo, memoria, GPU-hours)
   ↓
Evaluation (mismo conjunto de prueba)
   ↓
Comparación de las dos corridas
   ↓
Registry / promoción
   ↓
API o CLI de inferencia
   ↓
Demo
```

## Caso de estudio

El caso no está fijado como dependencia. El preferido inicial puede reutilizar trabajo geoespacial explorado antes (dataset + modelo preentrenado) si el cómputo lo permite. El respaldo es un modelo y un dataset más livianos.

Ver [ADR 001](../decisions/001-task-selection.md).

## Separación de responsabilidades

Siguiendo el primer informe (sección 5):

- **Infraestructura MLOps:** pipeline, tracking, registry, comparación, API. No “hace” el entrenamiento más rápido.
- **Estrategias evaluables:** baseline vs optimizado (LoRA, mixed precision, etc.). Explican el ahorro, si existe.
- **Caso de estudio:** dataset, modelo preentrenado, métricas de calidad e input/output de `/predict`.

Cambiar el caso no debe exigir rediseñar el núcleo. No se atribuye a Tune un speedup que produzca una técnica concreta.
